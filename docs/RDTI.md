# R&D 报告（RDTI）模块设计

- 状态：第一版已实现（见第 9 节），IP 归属等问题仍待确认
- 日期：2026-11-02
- 相关：[ADR-0009](adr/0009-rdti-report-module.md)、[ROADMAP](ROADMAP.md)

把 RDTI 技术报告从「读材料、找缺口、追资料、写报告」的手工流程，变成证据可追溯的半自动流程。AI 只写初稿和建议，每一步都有人工审核。

本模块做成系统内的业务模块 `modules/rdti`，挂在 Grants 产品线的项目（`items`）上，不做独立服务，也不做 Frappe 连接器。原因见 ADR-0009。

## 1. 原需求在系统里落在哪

| 原需求 | 系统现状 | 处理方式 |
| --- | --- | --- |
| Client（客户，可关联多个实体） | `clients` + `client_entities` + `contacts` | 直接复用 |
| Project（客户 + 财年下的 R&D 项目） | Grants 财年看板上的一行 `items` | 直接复用，RDTI 数据挂在 item 上 |
| Activity / EvidenceChunk / ElementAssessment / ChecklistItem / ReportSection | 无 | `rdti` 模块的新表 |
| Document（上传文件、版本） | 路线图「文件」，未做 | 做成全系统共用的文件模块，RDTI 是第一个使用者 |
| 文档解析（PyMuPDF、python-docx） | 无 | 放在文件模块，作为通用的文本提取能力 |
| 大模型适配层 | 预留 `platform/ai_gateway` | 先做最小版，RDTI 和邮件回复草稿共用 |
| 规则库（RDTI 要素与写作规范） | 无 | 存成可编辑的配置数据，不写死在代码里 |
| 随 Checklist 发给客户的邮件草稿 | 邮件模块已规划 | RDTI 生成文字；邮件模块上线后可存成 Gmail 草稿 |
| 人工审核、可追溯 | 命令总线：审计、撤销、事件 | 直接继承 |
| 后台处理 | worker + scheduler + 事件订阅 | 直接使用 |
| 多用户、权限 | 用户、角色、Grants 工作区权限 | 直接使用 |
| pgvector 语义检索 | 无 | 第一版不需要（见第 3 节） |

## 2. 分层

所有产品线都会用到的能力放平台层，RDTI 专属的判断逻辑放业务模块。以后做 EMDG、State Grants 时只是换一套规则。

| 层 | 位置 | 内容 | 其他使用者 |
| --- | --- | --- | --- |
| 平台 | 文件模块 | 上传、加密存储（澳洲区域）、版本、按客户隔离、文本提取（保留页码、段落位置和 PDF 坐标） | Engagement Letter、邮件附件、客户上传页 |
| 平台 | `platform/ai_gateway` | 统一调用大模型：可换模型、不用于训练的条款、客户同意校验、脱敏、调用留痕和费用 | 邮件回复草稿 |
| 业务 | `modules/rdti` | Activity、证据段落、要素评估、Checklist、报告段落、核查；规则库；Word 导出 | 仅 Grants |
| 业务 | `modules/mail`（已规划） | Checklist 邮件存成 Gmail 草稿；客户回信挂到项目 | 所有产品线 |
| 对外 | 客户上传页（以后） | 客户按 Checklist 上传，文件归到对应缺口 | Accounting 收资料 |

`rdti` 与系统其他部分只通过三个点相连：`item_id`、文件模块的文件 id、AI 网关。证据审核引擎写成不依赖系统内部结构的纯函数（输入文本段落和规则，输出评估），方便测试，以后也可以单独打包。

## 3. 数据模型

新表都写在 `modules/rdti/models.py`，通过 Alembic 迁移创建，会自动出现在「数据是怎么存的」页面，中文说明补在 i18n 的 `dataModel.tables`。

| 表 | 归属 | 关键字段 | 说明 |
| --- | --- | --- | --- |
| `clients` | 现有 | — | 可加客户级字段「AI 处理同意」 |
| `items` | 现有 | — | 原需求的 Project |
| `files` / `file_versions` | 文件模块 | owner_kind、owner_id、存储位置、哈希、版本号 | 原需求的 Document |
| `rdti_activities` | RDTI | item_id、编号、名称、kind（core/supporting）、supports_activity_id | Supporting 关联到 Core |
| `rdti_evidence_chunks` | RDTI | file_version_id、页码、段落位置、PDF 坐标、文本、activity_id（可空） | 可引用的最小单位；一次解析用一条批量命令写入，避免审计记录过多 |
| `rdti_element_assessments` | RDTI | activity_id、要素、覆盖程度（sufficient/partial/missing）、理由、关联证据、来源（ai/human）、规则版本 | 人工改过的不被 AI 重跑覆盖 |
| `rdti_checklist_items` | RDTI | activity_id、要素、问题、首选文件、替代资料、示例、状态、已收到的 file_id | 状态：草稿 / 已发送 / 已收到 / 已关闭 |
| `rdti_report_sections` | RDTI | activity_id、章节、正文、是否锁定 | 锁定的段落不被重写 |
| `rdti_report_claims` | RDTI | section_id、起止位置、文本哈希、状态、来源、确认人和时间 | 核查模式的论点，见第 5 节 |
| `rdti_claim_citations` | RDTI | claim_id、chunk_id、引句在 chunk 里的起止位置、支持程度（supports/partial/contradicts）、理由、核对时的 file_version | |
| `rdti_rule_sets` | RDTI | 名称（RDTI / EMDG…）、版本、内容（JSON） | 仓库里放一份 YAML 种子，管理员可在界面修改 |

关于 pgvector：一个项目的材料通常只有几十到几百段，按 Activity 直接交给模型就够了。等做跨项目的「历史知识库」时再加，到时只是给 chunk 表加一列向量。

## 4. 菜单和界面

RDTI 从项目进入，不单独开大菜单。

| 入口 | 内容 |
| --- | --- |
| Grants 看板 → 项目抽屉「R&D 报告」标签 | 进度摘要（Activity 数、缺口数、Checklist 未回复数），按钮「打开工作台」 |
| R&D 报告工作台（每个项目一页） | 四个子标签：材料 / 证据评估 / Checklist / 报告；左侧 Activity 列表 |
| Grants 看板镜像列 | 证据覆盖率、Checklist 待回复、报告状态；可筛选、可触发自动化 |
| 「我的工作」首页 | 新卡片「等客户补材料的 Checklist」 |
| 客户页 | 「文件」标签（文件模块提供） |
| 设置 → Grants 工作区 | 「RDTI 规则库」（管理员） |
| 设置 → 系统 | 「AI 使用记录」：模型、用量、费用、关联客户 |

权限沿用 Grants 工作区角色：member 可上传和评估，manager 可锁定和导出。自用阶段用功能开关只对指定用户显示。

## 5. 报告核查模式

报告写完后打开「核查模式」，全文按「论点」切分并着色。点任何一个有依据的论点，右侧显示原始资料里对应的那一段，并高亮原句。论点不等于自然段：可以是半句、一句，或连着几句讲同一件事的话。

### 5.1 四种状态

| 状态 | 样式 | 能否点击 | 含义 |
| --- | --- | --- | --- |
| 有依据 | 绿色下划线 | 可以 | 至少一段原始资料支持，且引文在原文中核对过 |
| 部分依据 / 需复核 | 黄色下划线 | 可以 | 资料只支持一部分（如数字对不上），或论点被人改过、资料换了版本 |
| 润色 / 过渡 | 灰色，无下划线 | 不可以 | 我们自己写的衔接、概括、引言，不含事实陈述 |
| 无依据 | 红色波浪线 | 可以（面板为空，提示去补） | 含事实、数字、日期、结果，但找不到资料支持；提交前必须处理 |

「润色」只能用于不含事实的句子。被标成润色的句子如果含数字、百分比、日期、产品名，系统会提醒。这是防止对 AusIndustry / ATO 不实陈述的主要防线。

### 5.2 点开论点后的右侧面板

- 来源文件名、版本、页码，原文前后各带一段上下文，支持的字句高亮
- 「打开原件」：PDF 跳到对应页并高亮，Word 跳到对应段落
- 一个论点可有多条来源，每条标「支持 / 部分支持 / 矛盾」
- AI 的一句话判断理由，例如「原文是延迟降低 30%，报告写成 40%」
- 操作：确认、换来源、添加来源（在资料里划一段）、标为润色、改写、加入 Checklist（缺资料就变成向客户索取的一项）

### 5.3 页面顶部

- 核查开关和统计条，例如：有依据 82% · 需复核 6 · 无依据 3 · 润色 24
- 筛选「只看红色 / 黄色」和「下一个」按钮
- 反向查看：在「材料」页点一段资料，能看到报告里哪些论点引用了它；从未被引用的关键资料也会提示

### 5.4 准确性

1. AI 写初稿时直接输出「论点 + 引用的资料段 + 原文引句」，不是写完再配。
2. 每条引句由程序在原文里精确查找，找不到就降为黄色，防止编造引文。
3. 独立的「支持度检查」：只给模型论点和引文，问是否支持，重点核数字。
4. 人工修改一句后，该句引用保留但变黄；「重新核查」只重算改过的句子。资料上传新版本时，引用旧版本的论点也变黄。
5. 确认、改来源、标润色都走 Command，活动记录里能查到是谁确认的。

### 5.5 导出

Word 导出两种：干净版（交付用）和审阅版（每个论点带脚注或批注，注明文件和页码）。有红色未处理时，导出干净版会先提醒。

## 6. 分阶段

每一步一个 PR。邮件模块和 RDTI 互不阻塞。

0. 准备（不写代码）：确定 IP 归属；把现有 Checklist 和报告写作规范整理成规则文件；准备 2–3 份脱敏样例材料。
1. 文件模块：上传、加密存储、版本、挂在客户和项目上、PDF/Word 文本提取。顺便完成 Engagement Letter 上传。
2. AI 网关最小版：一个模型供应商、客户同意校验、调用留痕和费用、测试用假模型。
3. RDTI ①：Activity、解析切段、按要素评估覆盖程度、人工修正。
4. RDTI ②：Checklist + 邮件草稿。
5. RDTI ③：报告初稿（带引用、逐段重写、锁定）、核查模式、Word 导出（干净版 / 审阅版）。
6. 自用验证后通过功能开关开放给同事。
7. 以后：客户上传页、历史知识库（pgvector）、财务模块、Portal 字段助手、EMDG 规则。对外商用取决于 IP 结论，暂不规划。

## 7. 待确认

- [ ] IP 归属：个人项目、公司项目，还是个人拥有 + 授权公司使用？若想保留个人商用的可能，证据引擎和规则库应拆成独立 Python 包，`rdti` 模块只负责界面、数据和流程。技术拆分不能代替书面约定。
- [ ] 顺序：建议文件模块先行（不依赖外部配置），邮件模块还要等 Google OAuth 设置。
- [ ] 大模型供应商，以及是否要求澳洲区域推理。
- [ ] 报告模板：建议沿用公司现有 Word 模板。

## 8. 数据安全

- 开发和测试只用脱敏或虚构材料（`backend/tests/fixtures`），真实客户资料不进 git、不进日志。
- AI 网关强制校验客户的「AI 处理同意」，未同意的客户不能送去模型。
- 文件加密存储，按客户隔离。
- 报告只是初稿，最终内容必须由顾问审核。

## 9. 实现状态（第一版，2026-11-02）

第 6 节的第 1–5 步合在一个 PR 里做了第一版，方便整体试用。

已做：

- 文件模块 `modules/files`：上传、版本（同名新版本会让引用它的论点回到待核查）、SHA-256、软删除。原件存在 `FLOW_UPLOAD_DIR`（Docker 里是 `uploads` 卷）。
- 文本提取 `platform/docs/extract.py`：PDF（页码 + 位置框）、Word（段落 + 表格行）、txt/md。扫描件 PDF 会明确报错，暂不做 OCR。
- AI 网关 `platform/ai_gateway`：`FLOW_AI_PROVIDER=fake | anthropic | off`。`fake` 是离线关键词版，本机试用和测试都用它；`anthropic` 调 Claude，只对勾选了「AI Processing Consent」的客户放行；每次调用记在 `ai_calls`。
- RDTI 模块 `modules/rdti`：活动（CA/SA 自动编号）、材料切段和分配、按要素评估（人工修改的结果不会被重跑覆盖）、Checklist 和邮件草稿、报告初稿、核查模式、Word 导出（干净版 / 审阅版）。
- 界面：Grants 项目抽屉里的「R&D report」页签，完整工作台在 `/rdti/<项目 id>`。
- 规则库 `modules/rdti/rules.py`（版本 `2026.11-1`）：各要素的问题、充分标准、首选/替代资料和示例。正式使用前要换成公司现有的 Checklist 和写作规范。

核查的准确性：AI 给出的每条引用都要能在原文里逐字找到（忽略大小写、空白和引号样式），找不到的引用标「待核查」，不算有出处。数字和日期必须出现在引用里，否则只算「部分支持」。人工确认需要至少一条已找到的引用；带数字或日期的句子标成「我们的措辞」要再确认一次。

还没做：

- 原件加密存储（目前依赖磁盘或卷加密）和按客户隔离的存储路径。
- 澳洲区域推理：现在的 `anthropic` 供应商走 Claude API 默认区域。正式对真实客户资料开启前要先定供应商和区域（第 7 节）。
- 脱敏、费用统计、OCR、客户上传页、历史知识库。
- 逐段让 AI 重写（现在是整份重新生成，锁定的段落保留）。
